# ADR-2026-10-17--docker-isolation-now-gvisor-later - Autonomous mode isolation: one Docker container per environment now, gVisor runtime later

- Date: 2026-10-17
- Status: accepted
- Context: Autonomous multi-runtime runs on a dedicated Ubuntu VPS cannot rely on per-command shell classification: harm of an arbitrary command (python script, node, binaries) is not decidable from its text, and runtime-native sandboxes cover only one runtime (Claude Code sandbox does not cover Antigravity, Codex or OpenCode). Isolation must contain every runtime and its subprocesses and deploy in one command.
- Decision: The VPS is the outer, disposable boundary. Inside it, one Along environment equals one Docker container managed by docker compose, generated by 'along env up'. The container mounts only the environment volumes (repo clone, runtime auth home), runs agents in their no-confirmation modes, and restricts egress to an allowlist (model APIs, GitHub, package registries, api.telegram.org). gVisor (runtime: runsc) is a later opt-in hardening switch, not part of the MVP. Kubernetes, Firecracker/Kata micro-VMs and per-command bubblewrap are out of scope. Windows interactive mode stays unisolated (human-in-the-loop, at the operator's risk).
- Consequences: Gates no longer try to be a security boundary in autonomous mode; the tool-nature classifier can be removed. Secrets the agents need (model API keys) are visible inside the container, so keys are per-VPS with spend limits and git credentials are repo-scoped. One container per environment means a compromised run can affect only that environment. gVisor adds syscall overhead and compatibility risk, hence deferred until the MVP works.
