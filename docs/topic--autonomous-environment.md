# Autonomous Environment Architecture & Docker Isolation

Comprehensive operational guide and architecture specification for isolated autonomous agent execution environments using Docker and Along Protocol.

---

## 1. Architectural Motivation & Threat Model

When executing autonomous AI agents without human confirmation on remote servers or VPS instances, host environments face substantial operational risks:
- Unbounded Command Execution: Arbitrary commands (e.g. bash scripts, package installers, build hooks) executed by agents cannot be verified as safe purely from static command text.
- Runtime Sandbox Asymmetry: Proprietary sandbox mechanisms (such as Claude Code bubblewrap sandboxes) cover only a single runtime, leaving other tools (OpenCode, Codex, custom scripts) uncontained.
- Host Contamination: Accidental file deletion, port conflicts, host credential leaks, or runaway background processes can disrupt server integrity.

As codified in [ADR-2026-10-17--docker-isolation-now-gvisor-later](./decisions/ADR-2026-10-17--docker-isolation-now-gvisor-later.md), Along adopts a container-based isolation model:
- The VPS acts as the outer, disposable physical boundary.
- Inside the host, each project environment maps strictly to one dedicated Docker container and one isolated host filesystem directory.
- Container boundaries enforce non-root user execution, strict volume boundaries, and an egress firewall allowlist.

---

## 2. Environment Architecture & Isolation Model

Each environment managed by `along env` adheres to an explicit isolation invariant:

```text
Host / VPS (/srv/along/envs/<name>/)
├── env.yaml        (Declarative settings, under 20 lines)
├── secrets.env     (API keys, git token, telegram credentials)
└── compose.yaml    (Deterministic docker compose specification)
        │
        ▼
Container Boundary (along-<name>)
├── Non-Root User: along (UID 1000, GID 1000 via setpriv)
├── Egress Allowlist Firewall (iptables + ipset: model APIs, GitHub, PyPI, npm)
└── Isolated Named Volumes:
    ├── repo          -> /workspace (Only writable project tree)
    ├── claude_auth   -> /home/along/.claude
    ├── opencode_auth -> /home/along/.opencode
    └── cache         -> /home/along/.cache
```

### Persistent State Invariant
All authentication tokens, agent login sessions, and Git repository clones are stored strictly inside named Docker volumes. Consequently:
- Stopping an environment with `along env down` preserves all agent login state and work in progress.
- Starting the environment again with `along env up` instantly restores operational readiness without re-authentication.

### Future Hardening: gVisor Runtime
The `env.yaml` schema includes an optional `gvisor: true` switch. When enabled on hosts with `runsc` installed, the generated `compose.yaml` appends `runtime: runsc` to provide kernel-level virtualization and protection against container escape vulnerabilities.

## 3. Directory Layout & Configuration Files

By default on Linux systems, environments are provisioned under `/srv/along/envs/<name>/` (configurable via `--dir` or the `ALONG_ENVS_DIR` environment variable).
Environment names are validated against `^[a-z0-9][a-z0-9_-]{0,62}$` to prevent directory traversal (`../`) and ensure container name safety.

### 3.1 env.yaml
Declarative environment descriptor serialized using ruamel round-trip mode and designed to stay strictly under 20 lines:

```yaml
name: myproj
repo: "https://github.com/actdim/along.git"
branch: "main"
runtimes:
  - claude-code
  - opencode
telegram_chat_id: ""
egress_allowlist: []
gvisor: false
image: "actdim/along-autonomous:latest"
```

### 3.2 secrets.env
Uncommitted secrets file with restricted filesystem permissions (`chmod 0600` on POSIX):

```env
# Model API Keys (scoped keys with spend limits recommended)
ANTHROPIC_API_KEY=sk-ant-...
OPENAI_API_KEY=sk-...
GEMINI_API_KEY=AIza...

# Git Repository Credentials (fine-grained repo-scoped token)
GITHUB_TOKEN=ghp_...

# Telegram Alerts & Interventions
TELEGRAM_BOT_TOKEN=123456:ABC-DEF...
TELEGRAM_CHAT_ID=-100123456789

# Autonomous Execution Mode & Self-Approval
ALONG_AUTONOMOUS=1
ALONG_ARCHITECT_SELF_APPROVAL=0  # Set to 1 to allow orchestrator architect self-approval without operator plan approval
```

### 3.3 compose.yaml
Deterministically synthesized compose specification created by `along env up` or `along env update`:

```yaml
# Generated by Along (along env) - do not edit by hand
services:
  runner:
    image: actdim/along-autonomous:latest
    container_name: along-myproj
    init: true
    restart: unless-stopped
    security_opt:
      - no-new-privileges:true
    sysctls:
      net.ipv6.conf.all.disable_ipv6: 1
    cap_add:
      - NET_ADMIN
    env_file:
      - secrets.env
    environment:
      ALONG_ENV_NAME: myproj
      ALONG_AUTONOMOUS: "1"
      ALONG_REPO_URL: "https://github.com/actdim/along.git"
      ALONG_REPO_BRANCH: "main"
      ALONG_RUNTIMES: "claude-code,opencode"
    volumes:
      - repo:/workspace
      - claude_auth:/home/along/.claude
      - opencode_auth:/home/along/.opencode
      - cache:/home/along/.cache

volumes:
  repo:
  claude_auth:
  opencode_auth:
  cache:
```

## 4. Docker Assets & Container Hardening

The autonomous runtime container is built from a single unified `docker/Dockerfile`:
- Base System: Ubuntu 24.04 LTS (Noble Numbat).
- Non-Root User: Replaces default `ubuntu` UID/GID 1000 user (`userdel --remove ubuntu`) and provisions user `along` (UID 1000, GID 1000).
- Privilege Separation: `sudo` is completely removed from the image and no sudoers files exist. The container entrypoint starts as root to initialize networking, then drops privileges permanently to UID 1000 via `setpriv --reuid=1000 --regid=1000 --init-groups --no-new-privs`.
- Runtimes: Node.js 20 LTS, Python 3.12, Along Protocol toolchain, `ipset`.
- Agent Tooling: Claude Code (`@anthropic-ai/claude-code`) and OpenCode (`opencode-ai`).

## 5. Egress Firewall & Network Allowlist

Container network egress is strictly regulated at container startup by `docker/init-firewall.sh`:
- Fail-Closed Architecture: The container entrypoint enforces root firewall application before any agent processes start. If the firewall fails or NET_ADMIN capability is missing, the container exits immediately with an error, preventing open fallback. The firewall can only be bypassed with explicit `ALONG_FIREWALL=off`.
- Preserved Docker DNS: The `nat` table is never modified, preserving Docker's embedded DNS (127.0.0.11) DNAT rules in `DOCKER_OUTPUT` and `DOCKER_POSTROUTING`.
- Nameserver Scoping: Outbound DNS traffic on port 53 (UDP/TCP) is permitted exclusively to nameservers configured in `/etc/resolv.conf` (or `ALONG_RESOLV_CONF`). Generic outbound queries to arbitrary destinations (e.g. 1.1.1.1, 8.8.8.8) are blocked to prevent DNS tunnelling.
- IPv6 Traffic Blocking: IPv6 INPUT, FORWARD, and OUTPUT chains are set to default DROP policy with fast ICMP rejection.
- Dynamic IP Refresh: An in-container background daemon periodically resolves allowlisted hosts and swaps the active `along-allow` ipset table every `ALONG_FIREWALL_REFRESH` seconds (default: 300 s).
- Mandatory Endpoints:
  - `api.anthropic.com` (Anthropic Claude API)
  - `api.openai.com` (OpenAI API)
  - `generativelanguage.googleapis.com` (Google Gemini API)
  - `github.com` (Git repository clone and push via HTTPS and SSH)
  - `pypi.org` and `files.pythonhosted.org` (Python package installation)
  - `registry.npmjs.org` (Node.js package installation)
  - `api.telegram.org` (Telegram alerts and long-polling supervisor gateway)

Custom host additions can be specified in `env.yaml` under `egress_allowlist` and are injected into the firewall via root-owned file `/run/along/egress.list`.

## 6. CLI Command Reference

The `along env` toolchain provides six operational subcommands:

### along env up
Create and start an isolated Docker environment:
```bash
along env up myproj --repo https://github.com/actdim/along.git --branch main
```
Flags:
- `<name>`: Environment name (required, must match `^[a-z0-9][a-z0-9_-]{0,62}$`).
- `--repo <url>`: Target Git repository clone URL.
- `--branch <branch>`: Target branch (default: `main`).
- `--dir <path>`: Base environments directory or custom environment path.

When docker or compose fails, `along env up` exits with non-zero exit code 1.

### along env down
Stop running container while keeping persistent volumes intact:
```bash
along env down myproj
```
When docker stop or compose down fails, `along env down` exits with non-zero exit code 1.

### along env status
Display environment details or list all configured environments:
```bash
# Show summary of a specific environment
along env status myproj

# Show machine-readable JSON status
along env status myproj --json

# List all configured environments on host
along env status
```

### along env logs
View or stream live logs from the runner container:
```bash
# Follow logs
along env logs myproj -f

# View last 50 lines
along env logs myproj --tail 50
```

### along env shell
Launch an interactive bash session inside the isolated container as non-root user `along`:
```bash
along env shell myproj
```

### along env update
Pull latest container image and restart the runner container (without unnecessary `--build` rebuilds):
```bash
along env update myproj
```
When docker pull or compose up fails, `along env update` reports the error and exits with non-zero exit code 1.

### Runner daemon (`along daemon`)

`along daemon start` (background) or `--foreground` (systemd: `docker/along-runner.service`) polls the
Telegram Bot API and runs `/task <slug>` through the orchestrator. Runtime files live in
`.along/.daemon/` (git-ignored):

- `daemon.pid`: PID on line 1 and the process start-time token on line 2, created exclusively. `status`
  and `stop` act only on the process that wrote it; a live PID with another or no token (PID reuse, or a
  file from an older version) is reported as `stale-pid` and never signalled.
- `daemon.json`: status, current task and `telegram_offset`, saved before each update runs, so a restart
  never runs an accepted command again.
- `daemon.log`: rotated to `daemon.log.1` above 5 MB.

#### Telegram Configuration & Precedence

Telegram settings are resolved uniformly via `alongkit.telegram` across daemon and feedback tools. Configuration merges through strict precedence (lower to higher priority, higher overwrites):
1. **Global Configuration**: `~/.along/config.json` (`transports.telegram` or `daemon` section).
2. **Local Repository Configuration**: `.along/config.json` (`transports.telegram` or `daemon` section).
3. **Environment Variables**:
   - Bot Token: `ALONG_TELEGRAM_BOT_TOKEN` or `TELEGRAM_BOT_TOKEN`.
   - Primary Chat ID: `ALONG_TELEGRAM_CHAT_ID` or `TELEGRAM_CHAT_ID`.
   - Allowed Chats: `ALONG_TELEGRAM_ALLOWED_CHATS` or `TELEGRAM_ALLOWED_CHATS` (comma-separated chat IDs).

Tasks run on a worker thread: `/status` answers during a run, a second `/task` gets "Runner busy", and on
SIGTERM the daemon stops polling and waits up to 20 s for the task. Commands older than
`max_command_age` (default 600 s; `daemon.max_command_age` in `.along/config.json` or
`ALONG_DAEMON_MAX_COMMAND_AGE`) are ignored with a reply. Transient poll errors back off
exponentially with jitter up to 300 s, resetting on success. HTTP 429 honors `retry_after`. HTTP 409
Conflict is retried within `conflict_window` (default 60 s; `daemon.conflict_window` in `.along/config.json`
or `ALONG_DAEMON_CONFLICT_WINDOW`); if it outlasts the window, the daemon notifies allowed chats and exits
with code 78. A rejected bot token (HTTP 401/404) exits with code 78 immediately. The systemd unit's
`RestartPreventExitStatus=78` prevents automatic restart on permanent configuration or conflict errors.
With `--worktree`, a clean worktree is removed but its `along/<slug>` branch is kept and named in the
reply; a worktree with uncommitted changes is kept whole.

Architect self-approval: Multi-agent orchestration requires human operator plan approval by default. When running headless in an autonomous environment without human operators, setting `ALONG_ARCHITECT_SELF_APPROVAL=1` enables the architect phase to self-approve the living plan and transition directly to the implementer phase. If unset or `0`, the orchestrator marks `plan_status: needs-approval`, updates session state to `needs-input`, and halts for external review.

## 7. Accepted Operational Risks

1. Model API Key Exposure: Agents executing inside the container have access to model keys injected via `secrets.env`. Operators should use per-VPS keys with strict budget limits.
2. Fine-Grained Git Permissions: Git credentials are handled via the ephemeral credential helper (`/usr/local/bin/git-credential-along`), ensuring tokens are supplied in-memory and never written to `/workspace/.git/config`.
3. DNS Tunnelling Through Docker Resolver: While outbound port 53 is restricted to the Docker embedded resolver (127.0.0.11), queries forwarded upstream could theoretically be abused for low-bandwidth DNS data exfiltration. Operators requiring air-gapped isolation should use explicit private upstream resolvers.
4. Telegram Bot Token: In the MVP, supervisor notifications share the environment credentials. Future milestones separate orchestrator and worker containers.
